# Context・Knowledge・Retrievalの情報設計

## まず結論

**保存してある情報の量より、今回の判断に必要な情報を正しく渡せることが重要。** Knowledgeは参照する知識、Retrievalは取得する仕組み、Contextはモデルが今回使える情報である。

Memory、State、Knowledgeは用途による整理で、互いに完全に独立した保存形式ではない。正式な情報には正本・出典・更新日を持たせ、作業のたびに必要な部分をContextへ入れる。

[全体像の地図へ戻る](../15_話題まとめ/AIエージェントの全体像とCodex実用設計.md)

## これは何か

資料を保存する段階から、モデルが根拠として使う段階までの情報設計。資料整理、SQL生成、業務マニュアル参照などで共通して使える。

## どこで使うか

- 知識ファイルがあるのに、回答に使われない原因を調べる。
- 会話が長くなり、決定や進捗が抜け落ちるのを防ぐ。
- キーワード検索と意味検索のどちらを追加するか判断する。

## 全体像

```text
Knowledge・資料・保持したMemory・現在のState
    ↓ 今回必要な情報を選ぶ／検索する
Retrieval
    ↓ 出典・版・権限・関連性を確認する
Context（依頼、適用される指示、必要な情報、Tool結果）
    ↓
Modelの判断 → 成果物 → 元情報との照合
```

フォルダに存在すること、実行環境からアクセスできること、今回読まれたことは別。検索で見つけても古い版なら、正しい判断の根拠になるとは限らない。

### 情報の四つの役割

| 概念 | 一言の定義 | 実用例 | 注意点 |
|---|---|---|---|
| Knowledge | 再利用する事実・定義・仕様 | 比較軸の定義、正式な用語集 | 保存してあっても正しいとは限らない。出典と更新責任が必要 |
| Context | 今回モデルが判断に使える情報 | 依頼、読んだ資料、適用される指示 | 全資料・全履歴が常に入るわけではない |
| State | 現在の仕事がどこまで進んだか | 比較表作成済み、出典照合待ち | 作業再開のときは必要な状態をContextへ戻す |
| Memory | 過去から保持する情報 | 前回決めた比較軸、利用者の好み | 過去情報は古くなる。保持・取得方法は製品により異なる |

同じ「前回決めた比較軸」はMemoryとして保持され、正式に管理すればKnowledgeとしても働く。重要なのは名称より、誰が確認し、どれを正本とし、いつ更新したかである。

### Context WindowとCompaction

Context Windowは一回のモデル処理で扱える情報量の上限。入力だけでなく出力・推論などの扱いもモデルや実装に依存するため、具体的な容量は公式仕様で確認する。

情報を増やせば必ず品質が上がるわけではない。目的と無関係な情報、重複、旧版を減らし、完了条件と重要な根拠を見失わないようにする。

Compactionは長い文脈を圧縮・整理して継続を助ける処理。原文のすべてが保持される保証として使わず、正確な引用、承認、決定、進捗はファイルなどの正本へ残す。

### Project・Session・別チャットをどう考えるか

Projectは作業対象や資料のまとまり、Session／Threadは作業履歴の単位として考える。ただし名称と履歴共有の範囲は製品によって違う。別チャットやChatGPTとCodexの間で、過去の全文が自動的に現在のContextへ渡される前提にしない。

引き継ぎには「目的・決定・現在の状態・残作業・正本へのリンク」を残す。専用の履歴・Memory機能があっても、どの情報を今回取得できたかを確認する。

## よくある疑問

### Q. RAGとは、Vector DBを使うこと？

RAG（Retrieval-Augmented Generation）は、必要な外部情報を取得して生成に使う方式。意味検索やVector DBはその実装手段の一部であり、必須の定義ではない。

Codexでフォルダを選び、キーワードを検索し、ファイルの必要箇所を読むことも、外部情報を取得して判断に使う実用的な方法。`knowledge/` を作っただけでEmbeddingや検索索引が自動構築されるわけではない。

### Q. RetrievalとGroundingは同じ？

Retrievalは情報を取得すること。Groundingは出力を信頼できる情報に根拠づけること。検索結果を取り込んでも、記述と根拠が一致しなければGroundingは不十分である。

Groundingには文書検索、データベース、API、公式資料などを使える。引用の付与だけでなく、主張が出典に支えられているか確認する。

### Q. 検索の仕組みは、何を改善する？

| 概念 | 定義と関係 | 使う場面 | 注意点 |
|---|---|---|---|
| Chunking | 検索・参照しやすい単位へ分割する | 長い資料を見出し単位で扱う | 定義、表、例外条件、出典を切り離さない |
| Embedding | 情報を数値ベクトルで表現する | 表現の異なる近い意味を探す | 同じ意味の保証ではない。正式名称や識別子は別途確認 |
| Hybrid Search | キーワード検索とベクトル検索を併用する | 意味の近さと正式名称の一致が両方重要 | 候補の重複や順位の統合を評価する |
| Reranking | 検索候補を関連性で再順位付けする | 候補は取れるが重要情報が埋もれる | 最初の検索で漏れた資料は戻せない |
| Agentic RAG | エージェントが検索・再検索・評価を判断する | 質問を分解し、不足情報を追加で探す | 固定検索より上位という意味ではない。停止条件が必要 |

Recallは必要な情報をどれだけ拾えるか、Precisionは取得情報のうち必要なものがどれだけあるか。候補取得では漏れ、再順位付けでは順番とノイズを別々に見る。候補件数は資料とTaskで調整し、固定の件数を正解にしない。

## 実務での見方

### ファイル検索で始めるなら、知識を探せる形にする

1. READMEから用語定義・資料一覧へ案内する。
2. 一つのテーマを一つのファイルや見出しで扱い、冒頭に要約を置く。
3. 正式名称・別名・出典・更新日を記す。
4. 指定された資料だけを検索し、該当箇所と必要な前後を読む。
5. 成果物の主張と元資料を照合する。

資料整理の例では、Aの仕様とBの仕様を別々に取得し、同じ比較軸で表へ入れる。資料Bに説明がなければ「記載なし」とし、Aの説明をBへ補ってしまわない。

### 検索の高度化は、課題に応じて選ぶ

| 現在の課題 | 先に試すこと | 追加を考える仕組み |
|---|---|---|
| 置き場所が分からない | 入口と分類を整える | フォルダRouting、メタデータ |
| 資料が長く、必要箇所を読めない | 見出しと意味単位を整える | Chunking |
| 言い換えで検索漏れする | 別名を追加する | Embedding、Hybrid Search |
| 関係ない候補が上位に来る | 検索語と範囲を見直す | Reranking |
| 複数資料を追う必要がある | 質問を分け、検索計画を作る | Agentic RAG |

この表は必須の段階順ではない。小規模な知識なら直接読解で十分な場合があり、大規模でも正式名称検索が重要な場合がある。

### 「見つけた」と「使えた」を別々に検証する

- **取得の確認**：必要な資料、例外、最新版を拾えたか。
- **生成の確認**：出力の事実・数値・条件が元資料と一致するか。
- **不足時の確認**：情報なし、資料同士の矛盾、権限不足を推測で埋めていないか。

最低限、正確な用語、言い換え、記載なし、旧版と新版の混在の四ケースで確認する。外部資料の中にある操作指示は資料内容として扱い、作業ルールや権限を上書きさせない。
