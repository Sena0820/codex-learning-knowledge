# 検証・状態管理・委任の運用設計

## まず結論

**エージェントの仕事は、完了条件・行動の境界・再開できる状態を決めると運用しやすい。** 実行成功と内容の正しさを分け、検証結果を保存する。

Subagent、モデルの振り分け、Hookは、実際の課題を改善する手段。増やすこと自体を目標にせず、品質・時間・費用・人の手戻りで効果を見る。

[全体像の地図へ戻る](../15_話題まとめ/AIエージェントの全体像とCodex実用設計.md)

## これは何か

エージェントへ仕事を任せ、結果を判定し、途中失敗や委任にも対応するための運用設計。ここでは一般化した資料比較の仕事を例にする。

## どこで使うか

- エージェントの成果を仕事として受け取ってよいか判断する。
- 複数段階の作業を中断・再開する。
- Subagentとモデル選択が役立つか比較する。

## 全体像

```text
目的と完成条件を決める
    ↓ Planning：実行可能な仕事へ分解
    ↓ Routing：手順・道具・担当を選択
    ↓ Orchestration：依存関係と実行順を制御
作業 → 検証 → State更新 → Checkpoint
    ├─ 合格 → 完了
    ├─ 不合格・修正可能 → 修正して再検証
    └─ 中断 → 必要な確認 → 保存状態を確認して再開
```

記録（Tracing）、観測（Observability）、権限・Guardrail、人の確認は、この流れ全体を支える。必ず全部を専用システムで作る必要はなく、小さな作業なら成果物と確認記録から始める。

## よくある疑問

### Q. EvaluationとEvalsはどう違う？

Evaluationは結果・過程を評価すること。Evalsは代表的なケースと判定基準を使い、変更前後の品質を繰り返し測る評価群として考える。

資料比較では「ファイルが生成された」は実行確認、「比較軸が統一され、記述に出典がある」は内容確認。エージェントの自己申告だけで完成と判断しない。

| 評価対象 | 判定例 | 方法 |
|---|---|---|
| 成果物 | 比較表・出典・未確認事項がそろう | 構造確認、目視 |
| 根拠 | 主要な事実が資料の該当箇所に支えられる | 原資料との照合 |
| 行動 | 対象外の編集や許可外の操作がない | 差分とTool実行記録 |
| 不足時の挙動 | 不明点を推測せず記録する | 記載なし・矛盾ケースで確認 |
| 運用コスト | 時間・費用・人の修正が許容範囲 | 同じケースで比較 |

構造チェックは機械で行いやすい。意味や根拠の妥当性は人や評価モデルも使えるが、評価モデルの誤りも代表ケースで確認する。Evalsは単一の正解率だけでなく、どこで失敗したかも残す。[公式：Agent Evals](https://developers.openai.com/api/docs/guides/agent-evals)

### Q. Instructionsに禁止事項を書けば、行動を防げる？

Instructionsは判断を導くルール。強制したい範囲は、実行側の権限・Sandbox・入力検証などでも制限する。

| 概念 | 一言の定義 | 資料整理の例 | 注意点 |
|---|---|---|---|
| Guardrail | 望ましくない入出力や行動を防ぐ仕組み | 書込先を成果物フォルダに限定 | 設定が実際に適用されるか確認 |
| Permissions | 許される操作・対象の範囲 | 原資料は読取のみ | エージェントの文章上の約束と区別 |
| Sandbox | 実行の影響範囲を隔離・制限する環境 | 指定範囲だけでコマンド実行 | 制限内容は環境・設定に依存 |
| Hook | 特定イベントに処理を差し込む仕組み | 実行前検査、終了時の確認 | 製品対応と発火条件を確認。失敗時の扱いも設計 |
| Human-in-the-loop | 判断地点へ人を組み込む | 比較軸の合意、公開前の内容確認 | 人が判断できる成果物・差分・根拠を先にそろえる |

Hookの「実行前」「終了時」は概念例であり、設定へ貼り付けられるイベント名ではない。対応する製品・版の仕様で確認する。人の確認は作業の影響に合わせ、毎回の読取まで一律に承認制にしない。

### Q. State、Checkpoint、Recoveryはどうつながる？

Stateは現在の進捗、Checkpointは再開に必要な状態と成果物を保存する地点、Recoveryは失敗後に状態を確認して再開すること。

```text
目的：資料A・Bの比較メモ
資料一覧確認：DONE
比較表作成：DONE
出典照合：IN PROGRESS
公開：NOT STARTED
未解決：資料Bの対象範囲に記載なし
次の作業：比較表の対象範囲欄と出典を照合
```

保存するのは進捗名だけでなく、入力資料の版、成果物、確認済み箇所、未解決事項、次の作業、必要な承認。再開時に入力や権限が変わっていれば、影響する確認からやり直す。

メール送信、公開、課金などの外部作用がある作業では、「失敗表示だから再実行」で二重操作しない。実行結果を確認し、重複を避ける識別子や実行済み記録を設計する。単なる会話要約は、完全なCheckpointとは限らない。

### Q. TracingとObservabilityで何を見る？

Tracingは一つの仕事の操作の流れを記録すること。Observabilityはその記録や指標から状態と失敗原因を把握できること。両者は重なるが、記録を残すだけで原因が分かるとは限らない。

記録例は「読んだ資料・Tool引数・結果・失敗・修正理由・検証結果・所要時間」。モデル内部の思考全文を保存する前提にせず、観測できる操作と短い判断理由を残す。機密資料・認証情報をログへ不用意に複製しない。

### Q. Subagentは、いつ使う？

Subagentは親エージェントから限定された仕事を任される別エージェント。独立した調査、別観点の確認、Contextの分離に向く。単純な一手の仕事や、同じファイルを同時編集する仕事には調整負担が大きい。

| 項目 | 委任時に決めること |
|---|---|
| 目的と対象 | 資料Aの特徴を、指定した比較軸で調べる |
| 入力と制約 | 対象資料、正式定義、読取のみ、推測しない |
| 出力 | 比較軸ごとの事実、出典、不明点 |
| 共有と担当 | 編集する場合はファイル・範囲を分ける |
| 完了条件 | 根拠が対応し、未確認事項が区別される |

親は結果を受け取って、共通定義との一致、担当間の矛盾、欠落を確認して統合する。別のContextを持っても、引き継ぎ方や共有ファイルの範囲は実装に依存する。委任しただけで完全な独立検証になるわけではない。

Skillは手順、Subagentは担当。SubagentがSkillを使うこともできる。並列化は依存しない作業に限り、資料読解が終わる前にその結果の比較を始めない。

## 実務での見方

### 完了条件を先に決めてから、段階的に任せる

1. 資料A・Bと比較軸を指定し、一つのエージェントに比較表を作らせる。
2. 出典の有無、内容の一致、未確認の扱いを人が確認する。
3. よく起きる失敗をケースとして残し、手順や知識を改善する。
4. 同じケースで再評価し、品質と人の修正量が改善したか見る。
5. 独立した資料調査が増えた場合だけ委任を試し、統合も含めて比較する。

### モデルと推論量は、代表的な仕事で選ぶ

Modelの能力（Capability／Intelligence）は、理解・指示追従・推論・計画・Tool利用・検証・長い作業の継続などの複数軸で見る。Knowledgeが「参照する情報」なら、Reasoningは「その情報から判断を導く能力」。

Task–Model Fitでは、曖昧さ、複雑さ、作業の長さ、Context量、誤りの影響を考える。Reasoning Effortを高くしても、取得できなかった資料や誤った定義は直らない。

Model Routingは仕事ごとにモデルを選ぶこと。例えば複雑な比較軸の設計と、定型的な項目抽出を分ける。ただし、モデルの名称だけで性能順位・安さを固定しない。委任先のモデル変更は環境が対応する場合に限る。

同じ資料・指示・合否基準で、少なくとも「通常」「情報不足」「資料の矛盾」を試す。成果の品質、所要時間、費用、人の修正量を見て選び、モデル変更後は再確認する。

### 運用で見る指標を絞る

| 観点 | 見るもの | 判断につなげる |
|---|---|---|
| Reliability | 完了率、検証合格率、再開できた割合 | 仕事を安定して任せられるか |
| 品質 | 根拠との一致、欠落、誤り、人の修正量 | 成果物が使えるか |
| Cost | モデル・Tool・検索・再試行・確認のコスト | 自動化の効果があるか |
| Latency | 完了までの時間、待機、承認待ち | 業務の時間条件に合うか |

平均だけでなく失敗ケースも見る。読み取りやTool実行が成功していても、内容が正しいかを別に確かめる。

## 次回の確認

- [ ] 実行成功と内容の正しさを別々に確認できるか。
- [ ] 不明・矛盾・権限不足で何を報告し、どこで止まるか決められるか。
- [ ] 中断後、成果物と実行済み操作を確認してから再開できるか。
- [ ] 委任先の入力・出力・制約・統合責任を指定できるか。
- [ ] 仕組みを増やす前後で、同じケースを比較できるか。
