# Snowflakeの分野まとめ

## まず結論

Snowflakeを復習するときは、まず `Notebookでどう触り始めるか` `どこを読んでいるか` `どこで遅くなるか` `UDFでどこが偏るか` `CTEをどう誤解しやすいか` `warehouseをどう選ぶか` `AIにどう正しくSQLを書かせるか` の7点で見ると整理しやすいです。細かい仕様を覚える前に、`Notebookの基本操作 -> scanの減らし方 -> 遅さの現象 -> UDF skew の見方 -> SQL側の見方 -> 基盤側の選択 -> AI向けの情報設計` の順で戻ると迷いにくくなります。

## どこで使うか

- Snowflake Notebook で何をどう書き始めればよいか迷うとき。
- Snowflakeのクエリが遅いとき。
- Snowpark UDF の並列実行が思ったより伸びないとき。
- SQL改善とwarehouse変更を切り分けたいとき。
- Query Profileをどこから読めばよいか迷うとき。
- AIにSnowflake SQLを書かせるとき、何を渡せばよいか整理したいとき。

復習の順番:
1. まず Snowflake Notebook の頻出スクリプトで `基本操作` をつかむ。
2. 次に micro-partition と pruning で `scanの減り方` をつかむ。
3. その後にスピルで `遅さの現象` をつかむ。
4. 次に JavaScript UDF のメモリ上限で `UDFが落ちる理由` を整理する。
5. 次に Snowpark UDF の skew で `並列でも遅い理由` を整理する。
6. その後に CTE 再評価で `SQLの見方` を整理する。
7. 最後に warehouse 世代で `基盤側の改善余地` を確認する。
8. AI活用をするときは、情報設計で `何を固定すべきか` を確認する。

話題をまとめて一気に復習したいときは、[Snowflakeの復習サマリー](./15_話題まとめ/Snowflakeの復習サマリー.md) から入ると戻しやすいです。

## よくある疑問

### Q. Snowflakeが遅いとき、最初に何を見る？

A. まず `不要な scan が多くないか` と `重いノードがどこか` を見ます。前者の入口は [Snowflakeのmicro-partitionとpruning](./20_トピック/Snowflakeのmicro-partitionとpruning.md)、後者の入口は [Snowflakeのスピル](./20_トピック/Snowflakeのスピル.md) です。

### Q. Notebook を使うとき、最初に何から覚える？

A. まず `session取得 -> 読む -> 加工 -> 確認 -> 保存` の流れを押さえます。入口としては [Snowflake Notebookの頻出スクリプト](./20_トピック/Snowflake%20Notebookの頻出スクリプト.md) を見ると、日常作業での使い方が戻しやすいです。

### Q. pruning は何をしている？

A. micro-partition ごとのメタデータを使って、関係のない partition を読まずに飛ばしています。`WHERE` 条件がうまく効くと scan 量が減ります。まずは [Snowflakeのmicro-partitionとpruning](./20_トピック/Snowflakeのmicro-partitionとpruning.md) を見ると整理しやすいです。

### Q. CTEに切り出したら、一度だけ計算される？

A. そうとは限りません。Snowflakeの非再帰CTEは、まず `名前付きサブクエリ` と考えます。重いCTEを複数参照するなら、`WITH` にしただけで安心せず [SnowflakeのCTE再評価](./20_トピック/SnowflakeのCTE再評価.md) を確認します。

### Q. ノード数を増やしたのに Snowpark UDF が速くならないのはなぜ？

A. `行数の均等` と `処理時間の均等` がズレている可能性があります。UDF は行ごとの重さがばらつきやすいので、一部ワーカーだけ重い行を引くと straggler になります。入口として [Snowpark UDFのデータスキューとDySkew](./20_トピック/Snowpark%20UDFのデータスキューとDySkew.md) を見ます。

### Q. JavaScript UDF の `thread memory limit exceeded` はなぜ起こる？

A. UDF を実行している JavaScript 側で、大きな JSON や配列、オブジェクトを作りすぎると起こります。特に View 内で `event_params` を UDF 生成し、その結果を `:page` や `LATERAL FLATTEN` で使うと、必要なキーだけに見えても UDF が全体を生成することがあります。詳しくは [SnowflakeのJavaScriptメモリ上限](./20_トピック/SnowflakeのJavaScriptメモリ上限.md) を見ます。

### Q. 遅いなら、まずwarehouseを大きくすればよい？

A. それだけでは弱いです。まず SQL や中間データ量の問題かを見て、その後に基盤側の改善を考えます。基盤側を見るときも、`サイズ` と `世代` は別です。詳しくは [Snowflakeウェアハウスの世代](./20_トピック/Snowflakeウェアハウスの世代.md) を見ます。

### Q. `SMALL / LARGE` と `gen 1 / gen 2` は何が違う？

A. `SMALL / LARGE` は計算資源の規模、`gen 1 / gen 2` はその規模の中で使う基盤世代です。規模を上げる話と、同じ規模で基盤を変える話を混ぜないことが大事です。

### Q. AIにSnowflake SQLを書かせるとき、最低限何を渡す？

A. `目的` `使用テーブル` `カラムの意味` `JOIN条件` `指標定義` `出力形式` を渡します。問いだけを渡すと、AIは意味を勝手に補完しやすいです。詳しくは [AIでSnowflake SQLを自動生成するときの情報設計](./20_トピック/AIでSnowflake%20SQLを自動生成するときの情報設計.md) を見ます。
